Clinic Appointment & Treatment Management System

Building CATMS, start to showcase.

A practical, conflict-free plan for five people to design, build, and demo CATMS — locally, transparently, and in a way every commit can be traced back to a person and a reason.

5 team members 6 delivery phases Local-first stack: PostgreSQL · Node · React GitHub-native workflow
00 · Framing

Why we're building this locally, by hand

A quick note on an intentional choice, before the plan itself.

This project is graded on the database: the entities, the constraints, the triggers and procedures that guarantee correctness, and the reasoning behind them. A managed backend platform that auto-generates CRUD APIs, auth, and admin panels would hide exactly the work we're being assessed on. So for this submission, everything runs locally — a self-managed PostgreSQL instance, a hand-written API layer, and a hand-written frontend — so that every constraint, trigger, and index in the system is something the team designed, wrote, and can defend live.

→

Production path (for later, not for this submission): because the schema and API are plain, portable SQL and REST — not vendor-specific — the same system could move to a managed Postgres host (Neon, Supabase, RDS) with the frontend on Vercel or Netlify and CI/CD fully automated, without redesigning anything. That's a good closing line for the demo: "this was built by hand on purpose, and here's how it would scale."

01 · Foundation

Technology stack

Every layer chosen so its inner workings stay visible — nothing that writes the schema or the auth logic for us.

Database

PostgreSQL 16

  • Local via Docker Composeone command, identical on every laptop
  • Hand-authored SQL migrationsnumbered, sequential .sql files — no ORM schema-magic
  • node-postgres (pg) driverparameterized queries only, called directly

Node.js + Express

  • REST APIone route group per module

Local environment

Docker Compose

  • Postgres + pgAdmin containersno cloud dependency to demo
  • .env-based configone template, no shared secrets in git
  • Seed scriptreproducible dummy data, one command to reset

GitHub

  • Repo + Issues + Projects boardsingle source of truth for tasks

03 · Process

Delivery methodology

A lightweight Scrum — enough structure to stay coordinated, not so much that it becomes its own project.

Cadence

  • Six sprints, roughly a week each (stretch to fit the actual term length).
  • A 15-minute check-in every 2–3 days — async on a group chat is fine, it just has to happen.
  • A 30-minute review-and-plan at the end of every sprint: what shipped, what's next, what's blocking whom.

Board

  • One GitHub Projects board: Backlog → In Progress → In Review → Done.
  • Every card labelled by module color (A–E) so load is visible at a glance.
  • No task is "in progress" without an assignee — prevents quiet duplicate work.
04 · Sequence

Project timeline

Six phases, each building on the last. Order matters here: scheduling depends on staff and patients existing, billing depends on scheduling, and reporting depends on everything — so later modules are naturally unblocked earlier when this order is followed.

0
Sprint 0 · Foundation

Repo, environment, and shared agreements

  • Repository created; branch protection and CODEOWNERS configured.
  • Docker Compose environment running identically for all five people.
  • Skeleton schema agreed: every table stubbed with primary/foreign keys, no business logic yet.
  • ER diagram, UI wireframes, and the design system's tokens agreed as a whole team.
Whole-team decision meeting — the schema skeleton and wireframes are locked together, not solo work. Team Lead drives repo/environment setup.
1
Sprint 1 · Schema, constraints & triggers

Each module's DDL, constraints, and business-rule triggers

  • Every member writes their module's tables, constraints, indexes, and triggers/procedures on its own feature branch.
  • Merged in dependency order: A and B first (nothing upstream depends on them), then C (needs doctors and patients to exist), then D (needs completed appointments), then E (needs invoices).
This dependency order is also why the module sitting in the middle of that chain — Appointment & Scheduling — is owned by whoever is already sequencing the merges: see Section 05.
2
Sprint 2 · Backend APIs

Endpoints, validation, and role guards

  • One route group per module, each calling parameterized queries or stored procedures — never string-built SQL.
  • Role checks (Reception / Clinician / Admin) enforced on every route, in addition to the database's own role grants.
3
Sprint 3 · Frontend screens

Each module's UI, on the shared design system

  • Every member builds their module's screens against the Sprint 0 design tokens — so five people's work still looks like one product.
  • Feature list frozen at the end of this sprint (see Section 11 — scope creep prevention).
4
Sprint 4 · Cross-module integration

Wiring the end-to-end flows

  • The flows that cross modules — book → complete → treat → invoice → pay → claim — get wired and tested together, in a whole-team integration session.
  • First full run-through of a realistic patient journey, start to finish.
5
Sprint 5 · Reporting, data & hardening

The five reports, dummy data at scale, and an NFR pass

  • Seed script populated to the volumes in the SRS (three branches, dozens of staff, hundreds of appointments).
  • The five report screens, built as charts, not just tables.
  • Security and performance pass: RBAC audit, parameterized-query audit, indexes verified with EXPLAIN ANALYZE.
  • Demo scenarios rehearsed once internally (overlap rejection, rollback, RBAC denial).
6
Sprint 6 · Polish & demo readiness

Freeze, rehearse, submit

  • UI polish — empty states, error states, responsive check down to tablet width.
  • Full regression pass against every REQ-ID in the SRS.
  • Feature freeze — only bug fixes merge from here.
  • Demo script (Section 12) rehearsed twice; release tagged v1.0-demo.
05 · Ownership

Team structure & responsibilities

One database module per person — the same person who argues for a requirement in the SRS implements and defends it live. Two members carry a light cross-cutting duty on top, matched to what their module already has spare capacity for.

Member 1

Team Lead & Appointment/Scheduling Owner

Module C

Owns booking, the doctor-overlap trigger, rescheduling, walk-ins, and the appointment status/audit log — the module every other module's timeline depends on.

Also carries

Repository and environment setup, branch protection & CODEOWNERS, schema-migration sequencing, sprint facilitation, and release tagging. This isn't a second job bolted on — sequencing the schema merges and owning the module in the middle of that dependency chain is one thread, not two.

Member 2

Branch & Staff Owner

Module A

Owns branches, employees, doctors, and specialties — the foundation every other module's foreign keys point back to.

Also carries

Design-system ownership: Tailwind tokens and the shared components (buttons, tables, modals, badges) every other module reuses, so five people's screens read as one product.

Member 3

Patient & Insurance Owner

Module B

Owns patients, emergency contacts, and insurance policies/coverage — the record that has to stay consistent across all three branches.

Also carries

Security & NFR ownership: RBAC role definitions, the password-hashing review, and a parameterized-query audit across every module before it merges to main.

Member 4

Treatment & Billing Owner

Module D

Owns the treatment catalogue, appointment-treatment records, and invoice generation — the module with the most transactional logic to get right.

Also carries

Data-integrity & testing ownership: the ACID demo scenarios (double-booking rejection, overpayment rejection, mid-transaction rollback) since billing is where these matter most.

Member 5

Payments, Claims & Reporting Owner

Module E

Owns payments, insurance claims, and the five management-report views — the module that turns everyone else's data into something the clinic (and the lecturer) can actually see.

Also carries

Demo & QA coordination: since reporting is what actually gets shown on stage, this member drafts and times the demo-day script in Section 12 and keeps the shared manual QA checklist up to date.

06 · Workflow

Git & GitHub workflow

Standard, boring, and on purpose — the goal is that two people are structurally unlikely to touch the same file in the same week.

main
dev
feature/*

Short-lived feature branches (one per task, coloured by module) branch off dev and merge back via reviewed PR. dev merges to the protected main only when a sprint's work is demo-ready.

Branching

main is protected — no direct pushes, always demo-ready. Everyone branches off dev as feature/<module-letter>-<short-task> (e.g. feature/c-overlap-trigger), kept short-lived — merged within two to three days, rebased onto dev first so it never goes stale enough to conflict.

Ownership

Database migrations, backend routes, and frontend module folders each belong to one member, enforced with a CODEOWNERS file so GitHub automatically requests the right reviewer. Migration files are numbered and claimed one at a time from the shared board, so two people can never claim the same migration number.

Review

Every PR needs one approving review and a passing CI check before it can merge — and never from the person who wrote it. Reviewers rotate rather than pairing the same two people every time, so schema knowledge doesn't stay siloed in one head.

Commits & PRs

Conventional Commits (feat/fix/docs/test/chore) for a history the lecturer can actually read. Every PR description states what changed, which REQ-ID(s) it satisfies, and how it was tested.

Continuous Integration

A GitHub Actions workflow runs on every PR: lint, plus a migration smoke-test that spins up Postgres in CI and applies every migration in order — a broken schema fails the PR automatically, instead of being discovered during the demo.

07 · Experience

UI/UX & signature features

The brief only asks for a UI good enough for QA. We're building one that makes every enforced business rule visible — which is what turns a database project into a demo people remember.

01

A calendar, not a form

A live, colour-coded doctor-availability calendar per branch, so the overlap rule is something you can see get enforced, not just trust is happening.

02

Rejections that teach

Every blocked action surfaces the exact rule that fired ("Doctor already booked 10:00–10:30 at Kandy") instead of a generic error — every enforced constraint becomes a visible moment in the demo.

03

A claim tracker, not a status column

Insurance claims rendered as a stepper — Submitted → Under Review → Approved/Rejected — instead of a plain text field.

04

A dashboard per role

Reception sees today's bookings, a doctor sees today's patient list, Admin/Finance sees outstanding balances — one landing screen each, not one generic homepage for everyone.

05

Reports you can explore

The five required reports as real charts (bar, line, donut) with a raw-table toggle underneath — satisfies the brief and looks like a product.

06

A one-click walk-in

A visibly distinct "Walk-in" action that skips the calendar entirely, so REQ-17 is something you demonstrate in three seconds, not explain in words.

07

"Why is this disabled?"

Hovering a greyed-out action (like recording a treatment before an appointment is Completed) names the exact rule blocking it.

08

Built for a reception desk

Responsive down to tablet width, visible keyboard focus throughout, colour choices that still read correctly for colour-blind users — usability that holds up, not just looks fine on a laptop.

08 · Proof, not claims

Non-functional requirements — execution plan

An NFR that can't be shown live is just a sentence in a document. For each one, here's exactly how we'll prove it during the demo.

Performance

EXPLAIN ANALYZE screenshots on the doctor-overlap check and each report query, taken before and after adding the SRS §6.3 indexes — an actual number on screen, not a claim.

Data integrity / ACID

A rehearsed "interrupt mid-transaction" moment showing a partially-applied booking never commits — atomicity, visibly.

Security

Live RBAC demo — log in as Reception, attempt a finance-only endpoint, show the 403 — plus one deliberate SQL-injection attempt against a search field, shown to fail safely.

Reliability & audit

Pull up the history/status log of one appointment that's been rescheduled and cancelled, proving nothing about it was silently lost.

Usability

A five-minute "cold user" test before demo day — someone outside the team books an appointment with zero instructions, timed; anything confusing gets fixed before the feature freeze.

Maintainability

The normalization note ready to explain on request, including the one deliberate, documented denormalization (the treatment-price snapshot) — and why it's there.

09 · Verification

Testing & quality assurance

Ownership follows the same module split — nobody is testing code they don't understand.

Per-module testing

  • Each module owner writes and maintains the test scenarios for their own business rules.
  • Member 4 (Treatment & Billing) additionally owns the cross-module ACID scenarios, since billing sits where most transactions converge.

Shared checklist

  • One manual QA checklist, one row per REQ-ID from the SRS.
  • Each member checks off their own module's rows before opening a PR; the whole team checks off every row together during Sprint 6.
  • Bugs tracked as GitHub Issues, labelled by module colour, triaged at the next check-in.
10 · Demo readiness

Dummy data & demo environment

A demo is only as good as the data behind it — and it has to survive being re-run if something goes wrong live.

Bulk seed data

One shared seed script — each member contributes their module's rows, merged and maintained by the Team Lead — producing the volumes set out in the SRS: three branches, roughly twenty staff, sixty to a hundred patients, hundreds of appointments across a simulated two-to-three month window.

Reproducible & safe to re-run

A fixed random seed and a single reset command return the local database to a known state — so if anything breaks mid-presentation, recovery is a two-minute reset, not a crisis.

A rehearsed "happy path"

Layered on top of the bulk seed: the same three or four named patients and doctors, used in every rehearsal and in the final demo, so the presenter never has to hunt through random data live.

11 · Guardrails

Risk management & conflict prevention

Every risk below is handled structurally, not just hoped away.

Merge conflicts

Prevented by folder ownership, numbered migrations, and short-lived branches — the same structure covered in Section 06, not an extra process.

Scope creep

The feature list is frozen at the end of Sprint 3. Anything proposed after that becomes a "next version" note, not a distraction before the demo.

Single points of failure

The rotating cross-review rule (Section 06) means at least two people understand every module by the time Sprint 6 starts.

Demo-day failure

Local Docker Compose plus a one-command database reset means a broken demo machine is a two-minute fix. A recorded backup of a full successful run is prepared as insurance.

Deadline slip

Sprint 6 is a built-in buffer: feature freeze first, polish and rehearsal after — so the last two to three days before submission are never the first time the full system is tested end to end.

12 · Showcase

Demo day script

A suggested running order — about ten minutes, with every member ready to speak to their own module during Q&A.

01

Architecture recap — thirty seconds on the three-tier diagram from Section 02.

02

Live booking, then a deliberate overlapping booking attempt — the rejection toast fires, naming the exact rule.

03

Walk-in creation — one click, no calendar lookup.

04

Treatment recording — shown blocked on a Scheduled appointment, then allowed the moment it's marked Completed.

05

Auto-generated invoice, a partial payment, and the outstanding balance updating live.

06

Insurance claim submitted — the stepper advances.

07

Reports dashboard — pick one chart, drill into the raw table beneath it.

08

One deliberate "attack" — a wrong-role access attempt or a SQL-injection try — shown blocked.

09

Design maturity, thirty seconds — the one documented denormalization (treatment-price snapshot) and why it's there on purpose.

10

Q&A — each member takes questions on their own module first.

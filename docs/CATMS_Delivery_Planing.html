00 · Target outcome

What this phase must actually deliver

The submission is not a mock-up and not only a schema. It is a complete local working slice of clinic operations whose correctness can be defended at the database level.

Phase 1 must work

Lecturer-ready local system

  • All 19 stored relations, their keys, delete policies, checks, indexes, procedures, functions, triggers, audit tables, and five reporting objects.
  • A thin API and role-based QA interface covering REQ-1 through REQ-36.
  • A reproducible dataset and one-command reset, plus automated and manual evidence for the critical rules.
  • A ten-minute live patient journey that still works with the internet disconnected.
Not in assessed scope

Explicitly deferred

  • No Supabase, Firebase, hosted database, generated CRUD backend, or third-party authentication dependency.
  • No patient self-service portal, SMS/email, external insurer integration, multi-currency, or branch-specific pricing.
  • No Kubernetes, microservices, mobile app, or production analytics platform.
  • No UI work that does not help exercise or explain a requirement.
→

Why local-first is the right assessment choice: the course project grades database design and correctness. Keeping PostgreSQL, SQL migrations, procedures, triggers, API validation, and UI logic visible lets the team show exactly where each guarantee lives. Later, the same containers and migrations move to a server without changing the domain model.

01 · Close the SRS TBDs

Decisions to freeze before implementation

These choices remove ambiguity from the SRS. They are recorded in an architecture decision log and may change only through team approval and an impact note.

D-01 · DBMS

PostgreSQL 16 is the only Phase 1 target. MySQL fallback is dropped so the team can use range/exclusion behaviour and one tested SQL dialect.

D-02 · Runtime

Development is local. PostgreSQL runs in Docker; API and UI may use local hot-reload. The frozen demo profile runs database, API, and web together from one Compose definition.

D-03 · Authentication

Use a short-lived JWT in an HttpOnly cookie. Password hashes are separate from clinical data. The API maps the authenticated role to a restricted database role per transaction.

D-04 · Time

Store appointment timestamps with time zone in UTC and display them as Asia/Colombo. Validate end > start and 15-minute scheduling increments.

D-05 · Overlap

The database is the final authority: a PostgreSQL time-range exclusion rule protects all non-cancelled appointments. The booking procedure returns a clear conflict message.

D-06 · Billing point

An invoice is ensured and recalculated automatically when a treatment is added to a Completed appointment. Catalogue price is copied into the line item at treatment time.

D-07 · Insurance

Policy terms calculate the eligible claim. Approved amount is the final insurance-covered amount; approval or rejection recalculates the patient's payable balance inside one transaction.

D-08 · Local transport

The demo is bound to localhost and can run without external network access. HTTPS and secure-cookie enforcement become mandatory in the later server profile.

D-09 · Delete policy

Clinical and financial history is retained. Master records are deactivated; dependent history uses RESTRICT. CASCADE is limited to true child/junction rows with no independent meaning.

D-10 · Completion gate

A stage is complete only when its artifact, tests, traceability links, review, and clean-machine run all pass. “Code written” alone is never Done.

Gate 0: the whole team signs off D-01 to D-10, the final ER model, table/column naming, money/time conventions, and the appointment/invoice/claim state transitions before the first schema migration is merged.

03 · Structure

Working architecture and rule placement

Three tiers, but one source of truth: anything that must remain correct under concurrency or API bypass belongs in PostgreSQL.

Presentation — React (Vite + Tailwind)

Role-based dashboards and QA screens. It never connects to PostgreSQL and never decides a financial total.

▲▼ REST · JSON · localhost (HTTPS on server)

Application — Node.js + Express

Authenticates, validates request shape, checks application RBAC, then calls a stored procedure/function or a controlled read query.

▲▼ parameterized SQL only

Owns tables, role grants, transactions, constraints, overlap protection, treatment gating, invoice/payment logic, audit history, and reporting views/functions.

05 · Gated sequence

Ground implementation timeline

Seven stages over roughly six weeks. If the real calendar is shorter, compress the duration—not the order or exit gates. A later stage may be explored on mocks, but it cannot be declared complete before its upstream gate passes.

0
Stage 0 · 2 working days · Freeze foundations

Decisions, model, contracts, and local baseline

  • Sign off D-01–D-10, the 19-relation ER model, cardinalities, naming, data types, state transitions, and delete policies.
  • Create repository protection, board, contribution rules, decision log, environment template, and shared API/error conventions.
  • Prove the blank local stack starts on all five laptops and that each member can open the DB, API health response, and UI shell.
  • Write the requirement-to-work-item sheet before assigning “In Progress”.
Exit Gate G0: clean-machine start succeeds; ERD and decisions are approved by all five; every requirement has an owner and planned proof. GALLAGE chairs and records the decision.
1
Stage 1 · 5 working days · Database foundation

Build the schema in dependency order

  • A and B deliver foundational tables and reference data first; authentication/role tables and the migration harness land with them.
  • C lands after stable Doctor, Patient, Branch, and Employee identifiers. D follows C; E follows D. Cross-module foreign keys are merged only through reviewed integration migrations.
  • Every relation includes PK/FK, nullability, unique/check constraints, explicit delete behaviour, comments, and its required index candidates.
  • Seed a tiny deterministic fixture—not the bulk demo data—to make every relation and relationship testable.
Exit Gate G1: all migrations apply from an empty database in order and roll forward with no manual repair; ERD matches the actual catalogue; key/constraint tests pass.
2
Stage 2 · 6 working days · Database behaviour

Implement the rules the project is graded on

  • C proves concurrent overlap rejection, rescheduling history, status-transition logging, cancellation retention, and walk-in behaviour.
  • D proves Completed-only treatments/notes, unit-price snapshotting, and automatic invoice recalculation.
  • E proves partial/full payment, overpayment rejection, claim transitions, insurance recalculation, and the five report queries.
  • A/B prove soft-deactivation, unique identities, doctor-specialty uniqueness, policy validity, and coverage limits.
Exit Gate G2: BR-1–BR-6 pass when invoked directly against PostgreSQL, including a two-session concurrency test and a forced rollback test. No UI is used as evidence for this gate.
3
Stage 3 · 5 working days · API and security

Expose controlled contracts, not raw tables

  • One API route group per module calls stored procedures/functions or parameterised reads; financial totals and audit fields are never accepted from the browser.
  • Standardise validation, pagination/filter rules, transaction boundaries, success payloads, and database-error mapping.
  • Implement login/logout, password hashing, application route guards, database role switching, and negative access tests for Reception, Clinician, Manager, and Admin/Finance.
  • Publish the API contract used by all UI owners and freeze breaking changes after G3.
Exit Gate G3: every required operation works through API tests; injection payloads are harmless; role-denied actions fail at both API and database levels; API contract is versioned.
4
Stage 4 · 6 working days · QA interface

Build requirement-oriented vertical slices

  • Build the shared shell first: login, role navigation, loading/empty/error patterns, tables, forms, confirmation dialogs, and exact database rejection display.
  • Each module owner builds the screens in Section 09 against the frozen API contract. Table-based report output is mandatory; charts follow only after values are verified.
  • Integrate the golden vertical slice: patient search/register → book/reschedule/walk-in → complete → record care → invoice → claim/payment → reports.
  • Freeze assessed features at G4. Any new idea goes to the post-assessment backlog.
Exit Gate G4: REQ-1–REQ-36 can be exercised from the browser; refresh and role changes behave correctly; all failure paths surface understandable DB-derived messages.
5
Stage 5 · 5 working days · Data, reports, NFRs

Prove the system at realistic scale

  • Generate the exact SRS scale: 3 branches, about 20 employees, 10–12 doctors, 8–10 specialties, 60–100 patients, 3–4 insurers, 15–20 treatments, and 150–300 appointments over 2–3 months.
  • Include scheduled/completed/cancelled appointments, about 15% walk-ins, active/expired policies, paid/partial/unpaid invoices, and approved/partial/rejected claims.
  • Manually reconcile a known sample for all five reports before adding charts. Capture EXPLAIN ANALYZE evidence and keep only indexes with a demonstrated purpose.
  • Run concurrency, performance, audit, RBAC, accessibility, backup/restore, and clean reset checks.
Exit Gate G5: NFR-1–NFR-9 evidence is recorded; seeded reports reconcile to expected totals; reset and backup/restore complete successfully on a second laptop.
6
Stage 6 · 4 working days · Release and showcase

Freeze, recover, rehearse, and release

  • Only severity-1/2 defects merge. Re-run the full traceability matrix from a freshly cloned repository and empty Docker volumes.
  • Prepare demo seed, offline dependencies/container images where permitted, database dump, screenshots, SQL evidence, and a short backup recording.
  • Rehearse twice under the real time limit: once on the primary laptop, once on the backup laptop; rotate questions so every member can defend their own and one adjacent module.
  • Tag the exact demonstrated commit v1.0-demo and lock the release bundle.
Exit Gate G6 / Go-live: two clean rehearsals, zero open critical/high defects, all deliverables present, contribution evidence reviewed, and a three-person go/no-go decision (Lead + QA owner + one independent module owner).

Definition of Ready for a task

A card may enter In Progress only when it has: one owner; REQ/BR/NFR links; dependencies resolved; expected database rule; API/UI behaviour; acceptance examples; reviewer; and a target stage. If any is missing, the card stays in Backlog/Blocked.

Definition of Done for a task

Migration or code is merged; tests pass from a clean database; owner documentation is updated; traceability evidence is linked; reviewer reproduces the success and at least one failure case; no unrelated warnings; and the feature works inside the full stack—not only in the owner's branch.

08 · Daily collaboration

Git, review, and communication workflow

A small-team trunk-oriented workflow: short branches, reviewed integration, continuous clean-database proof, and an explicit blocker rhythm.

main
dev
feature/*

Short-lived feature branches (one per task, coloured by module) branch off dev and merge back via reviewed PR. dev merges to the protected main only when a sprint's work is demo-ready.

Branching

main is protected — no direct pushes, always demo-ready. Everyone branches off dev as feature/<module-letter>-<short-task> (e.g. feature/c-overlap-trigger), kept short-lived — merged within two to three days, rebased onto dev first so it never goes stale enough to conflict.

Ownership

Database migrations, backend routes, and frontend module folders each belong to one member, enforced with a CODEOWNERS file so GitHub automatically requests the right reviewer. Migration files are numbered and claimed one at a time from the shared board, so two people can never claim the same migration number.

Review

Every PR needs one approving review and a passing CI check before it can merge — and never from the person who wrote it. Reviewers rotate rather than pairing the same two people every time, so schema knowledge doesn't stay siloed in one head.

Commits & PRs

Conventional Commits (feat/fix/docs/test/chore) for a history the lecturer can actually read. Every PR description states what changed, which REQ-ID(s) it satisfies, and how it was tested.

Continuous Integration

Every PR runs formatting/lint, unit/API tests, a clean PostgreSQL start, all migrations from zero, the small seed, database rule tests, and a build of API/UI. A broken schema or stale contract blocks merge.

10A · Proof, not claims

Non-functional verification plan

Each SRS NFR has a measurable test, retained evidence, and an accountable owner. Only a small selection is shown live; the full evidence remains available for lecturer questions.

Performance

Owner: GALLAGE + BANDARA. NFR-1: 5–10 concurrent booking attempts, accepted/rejected within 200 ms in the target dataset. NFR-2: each report under 2 s. Retain timed runs and EXPLAIN ANALYZE before/after justified indexes.

Data integrity / ACID

Owner: Willaddara. Force a failure after the first step of multi-step booking, invoice, and payment operations; assert that no partial rows or totals remain. Run two-session collision tests to show one conflicting booking succeeds and the other fails.

Security

Owner: LIYANAGAMAGE. Role matrix tests at UI, API, and PostgreSQL; password-hash inspection; secrets scan; parameterised-query review; one injection payload and one direct database permission denial.

Reliability & audit

Owner: GALLAGE. Reschedule and status audit trails retain actor, timestamp, old/new state and reason; backup and restore retain the same record counts and a checksum/reconciliation sample.

Usability

Owner: PILAPITIYA. A non-team student completes patient search and appointment booking with no verbal instruction; keyboard focus, error text, role navigation, tablet-width layout, and empty/loading states are checked.

Maintainability

Owner: GALLAGE + Willaddara. Clean migration from zero, schema comments, updated ERD/data dictionary, 3NF/BCNF proof, and the explicit treatment-price snapshot justification all agree with the released database.

10B · Verification gates

Testing and acceptance strategy

Every important rule is tested at the lowest level that owns it, then repeated through the API and one end-to-end browser path. The author writes tests; a different owner reproduces acceptance.

Layer 1–2 · Database and API

  • Schema tests: keys, nullability, unique/check constraints, FK/delete actions, role grants, views, migration order.
  • Rule tests: valid case, boundary case, invalid case, and concurrent case where relevant.
  • Procedure transaction tests: success commits all effects; induced failure rolls back all effects.
  • API contract tests: validation, role, status code, stable error code, response shape, pagination/filtering, injection payload.

Layer 3–4 · Integration and browser

  • Golden patient journey across all five modules, run after every integration session.
  • Role journeys for Reception, Clinician, Manager, Admin/Finance, and deliberate forbidden actions.
  • One manual checklist row per REQ-1–36 and NFR-1–9, with expected/actual/evidence/owner/reviewer fields.
  • Clean install, reset, backup/restore, offline-start, tablet-width, and wrong/empty data states.

11 · Reproducible local operation

Data, environments, and demo recovery

The team maintains three predictable data modes and two runtime profiles so development remains fast while the lecturer demonstration remains stable and offline-capable.

Data mode 1 · Tiny test fixture

Minimum deterministic rows needed for fast automated tests: every role, status, payment state, claim state, and one cross-module patient journey. Each owner maintains their portion; BANDARA validates shared financial expectations.

Data mode 2 · Realistic bulk dataset

12 · Guardrails

Risk, change, and recovery controls

Every material risk has an early signal, an owner, and a response. Risks are reviewed at each integration meeting, not only near submission.

Merge conflicts

Signal: branch older than three days or two people editing one migration. Response: split work by contract, rebase daily, and never edit an already-shared migration; add a new corrective migration.

Scope creep

Signal: work item has no REQ/NFR or demo purpose. Response: move it to post-assessment backlog. Features freeze at G4; database correctness, tests, recovery, and required UI are protected.

Single points of failure

Signal: only one person can explain or run a module. Response: named deputy, rotating review, paired walkthrough, and one-page module runbook. GALLAGE's integration responsibilities are specifically duplicated with PILAPITIYA.

Demo-day failure

Signal: offline start/reset or backup-laptop rehearsal fails. Response: no release sign-off until both machines pass; keep golden reset, dump, pre-pulled dependencies, screenshots, and recording.

Deadline slip

Signal: any gate slips by more than two working days. Response: cut P1 polish, move available member to the blocker, keep Stage 6 as release buffer, and present only tested functionality.

14 · After assessment

Path from local showcase to a real server

This work starts only after v1.0-demo is frozen. It reuses the same migrations, API contract, tests, and container boundaries; it does not introduce a separate “cloud version” of CATMS.

P1

Production requirements and threat review

  • Confirm hosting budget, expected staff concurrency, clinic connectivity, retention, backup, recovery, privacy, audit, domain, TLS, and operational ownership.
  • Resolve whether PostgreSQL is self-hosted on a VPS or managed; keep PostgreSQL 16 compatibility either way.
Gate: approved production architecture, data classification, recovery objectives, and cost owner.
P2

Harden configuration and infrastructure

  • Separate development/staging/production environments and secrets; require HTTPS, secure cookies, restricted network access, least-privilege DB users, log redaction, rate limits, and health monitoring.
  • Automate database backups with encryption and retention; rehearse restore to a separate environment.
Gate: security checklist, backup/restore drill, and staging environment pass.
P3

Deploy the unchanged release candidate to staging

  • Build immutable API/web images from a tag, apply migrations once through a controlled deployment job, and use non-production staging data.
  • Run the entire automated suite, performance tests, RBAC review, browser journey, and rollback rehearsal against server networking/TLS.
Gate: staging sign-off by delivery, security, QA, and clinic representative.
P4

Pilot one branch, then expand

  • Train a small pilot group, import only validated real data, monitor errors/performance, maintain a rollback window, and collect workflow feedback.
  • After pilot acceptance, roll out branch by branch with support contacts, incident process, monitoring, and scheduled backup-restore tests.
Gate: signed pilot acceptance and operational handover. Real patient data is never placed in the lecturer-demo environment.
→

Portability principle: only environment endpoints, TLS/secret management, storage/backup, monitoring, and capacity change. Tables, constraints, procedures, report semantics, API contracts, and tests remain the same unless a versioned migration deliberately changes them.
